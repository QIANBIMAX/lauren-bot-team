# Team 对照组织图审查与改进计划

审查基线：`ac64e6b`。对象：Team 的 7 个角色、BotMRR 与兼容 JSON、独立角色指令、kit Team/任务/验证/合并/经验库实现、Schema、Team 演示和测试。

结论：Team 的文字职责总体接近图片中的工程核心，但不能认定“严格符合且整链已实现”。主要问题是指令与运行实现不一致、交接缺少程序记录与约束、通用命令绕过角色边界、合并幂等路径能在验收失败时报告完成，以及 Nancy/规则反馈仍缺持久闭环。

本报告仅提出修改计划，没有修改运行代码。以下源码行号以审查基线为准；后续修改后应按函数名定位。

## 一、审查口径与合理裁剪

本图是用户指定的目标规格，不验证图片对原演讲的转述是否准确。

Team 作为独立精简产品线，可以只保留两个工程 bot，暂不实现工程③④、Eggbot、Tsuki、Potato、Crumb、四来源外围监控。此为范围裁剪，不算 Team 缺陷，也不能因此把 Team 标为完整复现全图。

保留下来的核心职责必须一致：

```text
用户 ↔ 幕僚长：方向、范围、重大决策
用户 ↔ Nancy：日常、待办、进度；日程范围明确标注
幕僚长 → Matcha → Eng-A/B → Developer → Verifier
Verifier 失败 → Eng 调度修复 → Developer → 新一轮独立验证
Verifier 通过 → 程序门禁 → 本地集成 → 集成结果 → 完成
失败经验 → 候选规则 → 实际验证/审核 → 发布 → Eng 后续开发包加载
工程执行状态 → Nancy；Nancy ↔ 幕僚长同步
```

工程 bot 只拆解和跟进，不写业务代码，这在 Team 与 Full 都是图中明确分工；不是“Team 暂不写，Full 才开始写”。真正写代码始终属于编程助手。

## 二、逐角色判断

| 角色 | 与图一致的部分 | 尚不一致或未落地 |
|---|---|---|
| 幕僚长 | 定范围、分派、把关、不写业务代码、复杂任务走 Matcha、进度转 Nancy | 简单任务直派 Developer 是项目自选捷径，图中没有；路由只有提示词，通用执行入口不检查交接；指令自身有未限定 Team 的硬禁条款 |
| Matcha | 工程主管，只调度不写码；向 A/B 指派 | 程序只写 assignment；缺少结构化工程包、接单回执和真实分派；拆分与 Eng 再拆分的层次边界还不清晰 |
| Eng-A/B | 新指令正确要求拆解、转交、跟进，禁止业务代码与验收通过 | 代码仍是 eng_stub，只可记备注；没有可验证的 Developer handoff；B 可给 A 的任务写备注；无法证明实际履职 |
| Developer | 真正实现、自检、提交 SHA，不能独立验收或集成 | 独立指令仍说“无 Nancy/Matcha/Eng”，只写接收幕僚长；没对 Team 交接、失败回流及规则回执做完整定义 |
| Verifier | 独立运行检查、留证据、不顺手改代码，职责描述正确 | 通用 record-check 可手填；检查缺逐轮绑定；失败没有自动形成给 Eng 的结构化修复包；独立指令仍排除 Team 角色 |
| Nancy | 进度、待办、减负、升级阻塞，不抢工程调度/写码/验收/合并 | 待办与进度本可只在会话；日程钩子不等于日历；routines 数组为空；摘要指标、负责人阶段和阻塞去重有缺口 |

## 三、关键发现与证据

### R1 · P1：角色权责并未覆盖通用任务入口

证据：`team.py:106–148` 用传入的 actor 字符串查角色，只约束部分 Team API；`protocol.py:277–306` 的状态迁移不核对角色；`protocol.py:310–361` 的 record_check 不核对验证者身份，还能写 artifact.commit。

临时目录探针已复现：以 Nancy 作为 actor 依次推进执行中、待验证，手填 executed=true、exit_code=0、pass、相同 commit 和不存在的日志路径后，可推进到验证通过，全程没有执行验收命令。

含义：现有字段校验确实生效，但“只有 Verifier 能提交可信验收”尚未由程序保证。此为普通运行入口问题，不需要假设攻击者拥有管理员权限。

改进：增加统一操作入口，绑定真实会话/执行身份、Team/profile、任务归属和操作权限；覆盖 record-check、状态迁移、产物提交、预算、规则审核/发布、merge 等通用命令。人工记录保留为诊断或显式导入证据，不能直接取得可信自动验收资格。权限不能只依赖调用方自报姓名。

### R2 · P1：Eng“拆解并转交”仅写进指令，运行时仍是占位

证据：`team.py:57–58` 只允许确认与占位状态；`assign_task` 仅允许 eng_stub；`eng_status_note:603–678` 只追加备注。没有结构化拆解或 Developer 接单记录。t1 脚本仍写 stub start、等待真实实现，没运行 Developer/Verifier。

临时目录探针另已复现：任务指派 Eng-A 后，Eng-B 仍能成功写入此任务的状态备注。

改进：建立实际工程协调能力；不要为了改名直接删除旧角色字段导致历史任务无法读取。由兼容映射迁移 eng_stub 到明确的协调能力。每项拆解须有输入、范围、验收、工作区、来源；保存 handoff、Developer 接收回执与运行 ID。未被指派者不能代替负责人提交操作性结果。

### R3 · P1：合并幂等分支可绕过失败验收和后置检查

证据：`merge/execute.py:299–350` 在完整预检之前，只要 bound 已是集成分支祖先，就走 already_merged 并可标完成；此分支没有同样执行后置检查。一般预检也未重新执行完整 verify-gate，合并后主要检查祖先关系与可选文件存在。

临时 Git 仓库探针已复现：状态待合并、verification.result=fail、checks 为空，bound 已在集成分支，且传入不存在的后置检查路径，仍返回 ok=true / already_merged / 已完成。

改进：所有路径先核对有效验收、真实 SHA、验收轮次和授权策略；“代码已包含”和“交付已验收完成”分开处理。幂等路径仍检查已绑定的集成验收结果；上次 post-check 失败不能在重试时自动转成功。目标基线变化进入重新评估/集成验证，不凭无冲突推定应用仍正确。

### R4 · P1：交接示例与 Schema 不一致，验收仍残留 Demo 默认值

证据：幕僚长指令约第107行把 parent_task_id 放在 team 对象内；权威 Schema 只允许顶层 parent_task_id。临时 Schema 探针已确认该示例触发 additionalProperties 错误。`add_child_task` 不接收完整工程包，创建时 parent_task_id=None，并继承 `create_task` 的 Demo 筛选验收命令。

改进：统一一种合法交接结构，区分 team_id、父业务任务、工程工作包和执行实例；不要把 team_id 当作父 task_id。Matcha 接收幕僚长冻结的范围和验收，Eng 只能细化执行步骤，不得降低必做项。子任务创建时必须传入或显式选择验收模板；通用业务不能默认“Demo 测试通过即验收”。所有文档示例纳入 Schema 校验。

### R5 · P2：Nancy“维护正本”的职责没有可靠的数据支撑

证据：Nancy 指令允许待办和进度本仅在会话里；`collect_child_statuses` 返回的是分派 Eng，不是当前实际执行者，也未返回逐任务更新时间。`summarize_team:521–574` 将验证通过、待合并、已完成聚合 doneish，容易被汇报误读，但当前输出仍保留原始状态，不能说它已直接伪造完成。

临时探针确认：仅验证通过的任务得到 doneish=1；同一阻塞在两个不同时间汇总，会留下两条升级记录。关键词防线还会拒绝“任务待合并，尚未完成”这样的事实备注。

改进：持久化任务视图、待办、截止点、负责人和更新来源；区分工程责任人、当前执行者、验收人。单独统计 verified/pending_merge/completed。阻塞按任务+原因+生命周期去重，明确解除状态；不要把历史阻塞全部当作当前阻塞。允许报告客观状态和引用只读 SHA，禁止的是修改权威结果而非说出这些词。

### R6 · P2：文档、导入包和独立角色指令存在冲突

证据：BotMRR 已改为工程拆解转交，team.manifest 和群说明仍称 stubs only；Developer/Verifier 独立指令说“一期无 Nancy/Matcha/Eng”。幕僚长 §3 将路由限定 Team，但 §4 复杂任务硬禁直派条款没有重复限定，Lite 使用同源指令时存在歧义。开工包节号引用也过时。

README、STATUS、docs/team 又出现“Full 四个完整写码 Eng”，与本图明确“工程 bot 也不亲自写代码”冲突。这是应立即纠正的文字错误。

改进：把公共职责与 profile 差异分开；Team 基础三角色使用明确的 Team 指令覆盖。BotMRR、JSON、SOUL、扁平 instructions、manifest、群说明、教程保持同一能力口径，防止另一格式导入后退回旧行为。优先保证独立导入包包含实际所需内容，不假设导入器会自动读仓库其他文件。

### R7 · P2：自动合并、失败规则和修复回流没有完整接线

证据：confirm 与 auto 合并代码都已存在；Team 包默认推荐 confirm，因此相对图片“通过后自动合并”属于刻意的保守差异，不是不存在合并器。规则库有候选/审核/发布，但 review 接收 approved 布尔值，不强制绑定探针；发布后没有强制反馈给 Eng 的加载回执。

改进：保留 confirm 默认，支持用户预先授权受控仓库/目标分支的 auto；一次策略授权后不每次重复确认。验证失败形成修复包交原 Eng，再交 Developer，重要范围变更由 Matcha/幕僚长裁定。规则经实际测试和审核发布，Eng 开工包记录适用规则版本；不能让 Verifier 兼任业务修复，也不能把每次环境故障机械地写成全局规则。

### R8 · P2：日程例程说明对“空包”的描述不准确

证据：BotMRR 中 routines=[]，Nancy 指令却指导用户在列表选择“每日进度摘要”后 Resume。包内没有此条目；独立 OMB 实例是否已有同名条目没有本次实测证据。

改进：要么按目标 OMB 支持格式真正提供默认暂停的模板并实测；要么明确“本包未创建例程”，指导用户显式创建。进度摘要/提醒是调度能力，不等于完整日历。Team 是否交付本地日程应明确：若保留精简范围，可只交付持久待办和按需提醒，并把完整外部日历列为后续，不作已有能力宣传。

### R9 · 范围差异：简单任务捷径并非严格原图路径

当前简单任务 Chief→Developer→Verifier 是此前为节省 token 设计的 Team 规则，不是程序 bug，但确实绕过图片中的 Matcha/Eng。

建议为 Team 引入明确路由策略：默认 engineering_chain，对所有开发/修复任务走 Matcha→Eng；可选 fast_path 仅对严格定义的小任务启用，默认关闭并记录原因。普通问答与纯状态查询不进入工程链路。

若继续以简单直派为默认，也可以保留现有设计，但产品应写“原图核心链路 + 简单任务捷径”，不能称“所有工程严格按图”。不要为省 token 把多项必做检查删成一项来符合捷径条件。

## 四、给 Grok 的修改顺序与验收

### T0：统一口径和契约，先避免继续漂移

1. 修复“Full 写码 Eng”等错误、Team/Lite 未限定条款、过期 stub 文案、独立 Developer/Verifier 指令和例程说明。
2. 确定默认路由策略及可选捷径；所有导入格式一致表达。
3. 修复 parent_task_id 示例及 Schema/运行字段不一致；工程包不再继承无关 Demo 验收。

验收：文档 JSON 示例全部通过权威 Schema；角色清单与禁止事项一致；干净 Team 包无相互矛盾指令；Lite 仍能独立直派。

### T1：先堵权限与合并完成条件漏洞

1. 实现统一角色/任务归属检查，并明确可信运行入口与本地 CLI 的权限模型。
2. 验收结果从独立执行回执生成；检查逐轮绑定；不允许 record-check 同时以不可信身份写开发产物与验收。
3. 修复 already_merged 绕过；普通与幂等合并统一核验；集成检查失败不能报完成。
4. 并行工作前为任务与 Team 状态提供原子写入和跨进程协调；集成分支串行，真实 worktree 隔离。

验收：本报告中的 Nancy 越权、伪造检查、Eng-B 越权备注、失败验收幂等完成探针全部从“接受”变为“明确拒绝”；合法只读进度汇报正常。

### T2：把工程拆解和交接变成真实链路

1. Matcha 负责跨工作包分配、依赖、冲突和负载；Eng 负责包内执行拆解、Developer 交接与修复跟踪，避免双方反复重拆。
2. 持久化 handoff_id、task/team/parent、Eng、Developer、验收引用、worktree、规则版本与接单回执。
3. 执行开始前检查路由与交接齐备；状态上区分已指派、已接单、执行中、待验，不能记录“执行中”就算已委派。
4. 接通真实 OMB 委派或已验证的执行器方式；如能力受限则保持受阻，单助手分角色演示只标模拟。
5. 验证失败回原 Eng，由其调度 Developer 修复并提交新轮次，范围/依赖变化才升级。

验收：A/B 各完成一个真实开发工作包；有输入、拆解、接单、代码 commit、独立验收、修复/通过记录；幕僚长不能在默认严格模式绕过中间层。

### T3：Nancy 持久化和进度减负

1. 增加持久待办与当前执行视图；读权威任务状态，不另造相互冲突的执行正本。
2. 阶段统计拆分；负责人按责任/执行/验收分别展示；待办完成有依据，不能由工程任务名称推定完成。
3. 阻塞去重与解除；状态变化触发摘要更新，平时按需汇总；例程选择暂停模板或显式创建方案。

验收：重启仍保留待办；同一阻塞不重复升级，解除后不继续报警；待合并明确报告未完成；“任务待合并，尚未完成”可正常记录；用户直接找 Nancy 即可了解状态。

### T4：失败经验反馈与端到端验收

1. 复用 lessons 模块，增加候选适用范围、真实探针和审核证据。
2. 发布与规则文件保持版本一致；Eng 的后续开发包记录加载回执，Developer 实际接收。
3. 增加新 E2E，不覆盖既有 t1 历史记录；t1 保留并明确只验证旧协议/状态。

验收场景：正常完成；首次失败后修复；规则防复发；旧 SHA/旧验收拒绝；失败 post-check 重试；Nancy 重启汇报；默认路由拒绝直派；启用 fast_path 的合法小任务；Lite 回归。

真实端到端至少一条穿过独立 OMB 助手/执行器；程序化 mock 用于故障分支，不算真实委派。macOS、Windows、Linux 的支持继续分别记录，不因这次 Team 修正就宣布三平台验收完成。

## 五、建议的最终权责表

| 操作 | 责任主体 |
|---|---|
| 目标、范围、验收定义/变更与预算批准请求 | 幕僚长把关，用户授权相应策略 |
| 工程工作包、依赖、Eng 分配 | Matcha |
| 包内拆解、开发交接、修复调度 | 被指派的 Eng |
| 业务代码、开发 commit、自检 | Developer |
| 独立验收执行与可信报告 | Verifier，通过可信程序接口记录 |
| 程序门禁、Git 集成与完成回执 | 合并程序按授权策略执行；幕僚长可请求，不得伪造结果 |
| 待办、进度视图、提醒、阻塞汇报 | Nancy |
| 规则候选 | Eng/Developer/Verifier 可提出，带来源 |
| 规则有效性验收 | Verifier |
| 规则发布策略 | 幕僚长按授权请求，由程序校验与发布 |

Team 保留 7 角色，不为修复核心链路新增 Full 外围角色。Nancy 和 Matcha 不能获得代码/验收/合并权；Eng 在任何产品线都不是写码角色。

## 六、本次验证记录与边界

- kit 现有测试重新运行：72 项通过；不代表新增需求已有覆盖。
- 临时目录探针确认：Eng 跨负责人备注被接受；Nancy 经通用接口可用手填信息推进验证通过；待合并事实备注被拒；同一阻塞多次汇总重复升级；嵌套 parent_task_id 示例违反 Schema；通用 Team 子任务仍继承 Demo 验收。
- 临时 Git 探针确认：验收失败且后置文件缺失时，already_merged 路径仍能返回成功并标完成。
- 未运行真实 OMB GUI、多助手委派和三平台端到端；未改用户运行任务；探针仅使用临时数据。
- 不报告精确完成百分比；修改完成后按上述行为验收，不能只增加提示词后就宣告程序已约束。
