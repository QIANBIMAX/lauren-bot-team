## 2. 角色与一期范围（以项目维护者批件 `m0/phase1-plan-v0.1.md` 为准）

完整图（**二期**）：Lauren ↔ Nancy + 幕僚长；专项 Tsuki/Potato/Crumb；Matcha + 4 Eng；云 coder → verifier；Eggbot / 外层定时。

**一期最小三角（v0.1 已批，M0/M1 只做这仨；不加 Nancy / Matcha）**：

1. **幕僚长**（Chief）— 统一入口：明确范围、拆任务、冻结验收、调度、汇总证据；默认不重复编码  
2. **开发助手** — 在独立工作区改代码、自检、按验证结果修复；不直接合并、不自批验收  
3. **验证助手** — 按原始需求与验收标准独立检查准确版本、留证据；默认不改待验收代码  

> 旧占位「Worker / Nancy」作废。Nancy 属二期进度协调，不得写入一期团队包。

### 2.1 状态机（批件对齐）

主路径：`待执行 → 执行中 → 待验证 → 验证通过 → 待合并 → 已完成`

补充态：**需修改** · **受阻** · **已取消** · **合并失败**

验证通过 ≠ 任务完成；须交付条件满足（含合并策略）后才算完成。

## 3. 硬边界

- 不做真实 Slack / 企微全量接入  
- 不碰生产权限  
- **一期 Pass：只落产物 + 记录，不自动合公司主仓**  
- **条件合并**（仅 Demo 本地集成分支）：默认可配置为 `auto` 或 `confirm`（需人点头）；**文档写死默认值 = `confirm`**；公司主仓永远不自动合  
- **一期**任务协议 JSON **禁止**直接携带大段业务 `content` / `code` / `patch`（开发助手在工作区改文件，不经协议正文塞代码）  
- （**二期**）Matcha + Eng bot 输出仍禁止代码字段；专项 bot 不走工程线；进度→Nancy，问题→幕僚长；Lauren 只看汇总  
- **一期**：进度与问题均由幕僚长汇总；验证结论以验证助手报告为准

## 4. 工程闭环（kit，对标 pstack）

参考：`pstack` / `pstack-claude` / `open-pstack` 的拆写验回流思路。OpenMausBot **不管**写码闭环细节，只提供队工作台与委派。

一期主路径（三角色，串行）：

```
用户需求 → 幕僚长（定范围/验收/调度）
        → 开发助手（独立工作区改代码并自检）
        → 验证助手（跑应用、留证据）
        → Pass：记档；按 MERGE_POLICY 对 Demo 本地分支 confirm/auto
        → Fail / 需修改：回开发助手修复再验
        → 受阻 / 已取消 / 合并失败：幕僚长汇总，不伪造成功
```

失败中可复用教训 → kit 候选规则/预检/回归 → 验证能抓住且不误伤 → 版本化回挂。

工程闭环实现放在 `lauren-team-kit`，对标 `pstack` / `pstack-claude` / `open-pstack`（必要时 `pi-pstack`）。OMB 只做队工作台与委派。

一期默认 coding：工作区内由开发助手引擎执行；kit 侧可另备 `shell`+DeepSeek / OpenHands 适配，不阻塞 M0。
