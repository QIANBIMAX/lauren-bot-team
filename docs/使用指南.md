# 使用指南（日常怎么用）

路径约定：在终端进入 clone 后的 lauren-bot-team 根目录，然后执行：

```bash
export PROJECT_ROOT="$(pwd)"
```

以下 Bash 示例使用该变量；每次新开终端需重新设置。

面向几乎没写过代码的人。假设你已经能打开项目文件夹，并且（最好）按 `docs/新手入门.md` 跑通过演示。

> 日期：2026-11-04（Asia/Shanghai）

---

## 1. 只跑演示（推荐新人）

不打开 OMB，也能看懂三个环。路径请换成你本机项目文件夹。

### C1：筛选能用

```bash
cd "${PROJECT_ROOT}/demo-app"
bash scripts/smoke.sh
```

成功时大概会看到：`SMOKE OK`

### C2：弄坏 → 打回 → 修好

```bash
bash scripts/smoke-c2.sh
```

成功时大概会看到：`C2 REWORK DEMO OK`  
（中间故意失败一轮是正常的。）

### C3：学过的坑下次拦住

```bash
bash scripts/smoke-c3.sh
```

成功时大概会看到：`C3 LESSON REUSE DEMO OK`

### 可选：工程工具层烟雾

```bash
cd "${PROJECT_ROOT}"
bash lauren-team-kit/scripts/c2_kit_rework_smoke.sh
bash lauren-team-kit/scripts/c3_kit_lesson_smoke.sh
```

成功时大概会看到：`C2 KIT REWORK SMOKE OK`、`C3 KIT LESSON SMOKE OK`

这些脚本在交付路径上已跑通过；照着跑一般会过。失败就把终端全文发给交付人。

## 2. 任务状态 / 证据目录在哪

### 2.1 演示应用留下的证据

在项目里的：

```text
demo-app/evidence/
```

常见子目录：

| 路径 | 含义（白话） |
|---|---|
| `demo-app/evidence/c2/round1/` | C2 第一轮：故意有缺陷，验收失败的记录 |
| `demo-app/evidence/c2/round2/` | C2 第二轮：修好后再验通过的记录 |
| `demo-app/evidence/c3/blocked/` | C3：同类缺陷被规则拦住 |
| `demo-app/evidence/c3/clean/` | C3：干净版本通过 |

用 Finder 打开这些文件夹即可浏览；里面常有 `report.json` 一类结果文件。

### 2.2 工程工具跑批留下的记录

```text
workspace/runs/
```

每个任务一个子文件夹（例如 `demo-c2`、`demo-c3`），里面常见：

- `task.json`：这条任务的协议与当前状态
- `logs/`：命令日志
- `checks/`、`artifacts/`：检查与产物（若有）

> 说明：`workspace/runs/` 里的内容通常不当作「要提交给别人的源码」；它是跑起来之后留下的痕迹。

## 3. 三个角色在 OMB 里怎么协作（理想流程）

> **再次说明**：三角色在 OMB 里的正式导入、互相委派、重启恢复，**尚未在本项目验收通过**。  
> 下面是「设计上应该怎样协作」的白话版，方便你对照；**不是**「已经在你电脑的 OMB 里点过一遍」的保证。

### 3.1 状态机（白话）

主路径可以记成一条流水线：

```text
待执行 → 执行中 → 待验证 → 验证通过 → 待合并 → 已完成
```

失败或要返工时，常见会变成：**需修改**（然后回到执行中再改）。  
另外还有：受阻、已取消、合并失败等（环境不行、人取消、合并条件不满足时）。

| 状态 | 白话 |
|---|---|
| 待执行 | 任务开好了，还没开工 |
| 执行中 | 开发助手正在改 |
| 待验证 | 改完了，交给验证助手 |
| 验证通过 | 检查真的跑过且合格（不是嘴上说） |
| 待合并 | 可以进入「合到演示本地分支」前的确认 |
| 已完成 | 交付条件满足，这条任务收工 |
| 需修改 | 验过了但不合格，打回修改 |

注意：**验证通过 ≠ 已经完成**。还要满足合并/交付条件，才会到「已完成」。

### 3.2 理想分工顺序

1. **你**提出需求（或演示场景）。
2. **幕僚长**划清范围与验收标准，签发任务，推进状态。
3. **开发助手**在指定工作区改代码、自检、交待验收版本。
4. **验证助手**按清单真跑检查、留证据，判定通过或不通过。
5. 不通过 → **需修改** → 开发再改 → 再验。
6. 通过 → 按合并规矩进入「待合并 / 已完成」（默认要人点头；只合演示本地分支）。

对照说明见：`lauren-omb-pack/groups/lauren-core.md`。

## 4. 什么叫「检查没跑就不能标通过」

验收清单里会有一类检查，标记为必须执行（技术名：`must_run`，可先记成「必跑项」）。

硬规矩（白话）：

- 必跑项**只要有一条没真正跑过**，就不能把任务标成「验证通过」。
- 「开发助手说没问题」不能代替验证助手跑出来的结果。
- 工程工具里有「验证硬门」：试图在没留合格检查记录时标「验证通过」，会被拒绝。

C2 的 kit 烟雾就是在演示：第一轮检查不合格 → 进「需修改」；补好检查记录后 → 才能「验证通过」。并且**不会真的去合公司主仓**。

## 5. 合并时你要记住的三句话

1. 默认 **confirm**：要人点头才合。
2. **只合**演示用的本地分支。
3. **绝不**自动合公司主仓。

详见 `docs/merge-policy.md`。

## 6. 不要做的事清单

- 不要把本包装成「OMB 源码 fork」去乱改上游。
- Lite 与 Team 是两条平行产品线：Import Lite 只有三角；Import Team 才有 Nancy私人助理 / 工程主管Matcha / 工程bot stub。日常优先私聊幕僚长，群可选。
- 不要在必跑检查没跑时，手工把状态改成「验证通过」并对外宣称完成。
- 不要配置成自动合公司主仓 / 生产分支。
- 不要删除或改乱 `lauren-omb-pack`、`lauren-team-kit`、`demo-app` 的顶层名字。
- 不要把真 API 密钥写进要外传的共享拷贝。
- 不要把「Windows / Linux 尚未验收」「OMB GUI 尚未验收」说成已经测通。
- 不要把未跑过的检查写成「已通过」。
