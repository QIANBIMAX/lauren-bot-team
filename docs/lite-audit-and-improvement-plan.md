# Lite 审查与改进计划

交付对象：Grok Bot 指挥官。审查基线：`ac64e6b`。计划尚未实施，不表示本次已修复运行代码。

结论：Lite 三角色职责与最小开发闭环的方向正确，已有状态机、验证字段门禁、本地真实合并、预算与恢复协议、经验库和测试。但执行真实性、角色权限、完成条件、预算恢复与独立交付仍需加固。能跑通 Demo 不等于新人环境、失败路径和三平台发布全部通过。

## 一、产品边界与目标链路

保持 Lite / Team / Full 平行，Lite 只包含幕僚长、Developer、Verifier，不要求安装 Team，不引入 Nancy、Matcha 或工程 bot。复杂任务在 Lite 中仍可由幕僚长切分后逐项交 Developer；任务大到超出预算或能力时明确受阻，不强制用户安装 Team。

目标链路：

```text
用户 → 幕僚长冻结目标/范围/验收/预算
     → Developer 在真实隔离工作区实现、自检、提交准确 SHA
     → Verifier 在独立环境执行必做项并生成可信证据
         失败 → Developer 修复 → 新轮次验证
         通过 → 程序预检 → 按策略确认 → 本地集成 → 集成验证
                                                  ↓
                                        合并程序记录完成，幕僚长汇报
失败经验 → 候选 → 验证/审核 → 发布 → 后续开发包加载
```

幕僚长负责协调、范围与策略把关，不亲自写业务代码；Developer 不能为自己的代码签发独立验收；Verifier 不顺手修改待验业务代码。合并器是程序能力，不增加第四个 bot。

## 二、逐角色与交付判断

| 对象 | 已有合理部分 | 改进重点 |
|---|---|---|
| 幕僚长 | 签发任务、定义范围、调度、汇总、请求合并 | 指令中的 Team 限制需显式限定 profile；完成不能靠手动状态迁移；预算提高要有真实授权依据 |
| Developer | 隔离目录、自检、提交 SHA、禁止合并与改验收 | 程序真正创建/约束工作区；提交产物与独立验收分权；失败后正确进入执行修复再待验 |
| Verifier | 实际运行检查、绑定版本、保存证据、不改代码 | 接通命令执行与可信回执；逐轮绑定检查；不能靠手填字段获得通过 |
| Lite 导入包 | 三角色独立、稳定无版本后缀命名、默认本地 confirm | 自包含指令与契约一致；单助手轮流扮演只能称演示，不算独立验收 |
| 共享 kit | 有真实 Git 合并与预算/恢复/经验库基础 | 修复通用入口绕过、合并幂等、恢复预算和状态持久化问题 |

## 三、问题清单

### L1 · P1：开发者可通过通用接口自填验收并标完成

位置：`protocol.py` 的 record_check、transition_task，及 CLI 对应入口。

本次纯 Lite 临时探针已复现：Developer 将任务推进待验证，填入 executed=true、exit_code=0、pass、两个相同的占位 commit 和不存在的日志路径，即可继续推进验证通过、待合并、已完成。没有真实执行命令或进行 Git 合并。

原因有两层：验证门检查字段而不执行命令；通用状态迁移只检查状态边，不检查操作身份，也没有在进入已完成时校验真实交付结果。

改进：可信运行入口绑定角色与任务；Developer 只能提交产物和自检，Verifier 只能提交独立检查回执，完成状态由合并程序依据有效回执写入。人工导入记录保留诊断用途，但不能自动获得可信验收/合并资格。不能把自报 actor 或可任意传入的布尔值当作权限凭证。

### L2 · P1：验收记录缺逐轮、逐项版本绑定

record_check 按 acceptance_id 更新检查，commit 绑定在报告总层；提交新版本或改变验收时，可能留下旧检查。日志存在、执行来源、命令与验收定义版本未被完整核验。

改进：每次提交形成独立 attempt，固定真实源 SHA、验收定义摘要、环境和命令；每条检查绑定该 attempt。独立执行器生成 stdout/stderr、退出码、起止时间和执行回执；新 commit、必做项或相关环境变化使旧报告失效。代码任务必须至少有一项可执行必做验收；纯文档等任务另定显式交付类型，不能用空检查冒充工程验收。

### L3 · P1：合并幂等分支和完成门禁不完整

继承 Team 审查中已实证的共享缺陷：`merge/execute.py` 的 already_merged 分支可在 result=fail、checks 为空且后置文件缺失时返回成功、标完成。普通预检也未完整复核验证门；后置主要是 Git 祖先关系与文件存在检查。

改进：普通与幂等路径统一检查身份、有效验收、真实 SHA、授权仓库/分支和交付回执。代码已包含不等于验收完成；上次后置失败不能在重试时被转为成功。目标基线前进时重评估；集成提交实际运行必要检查。保留本地 confirm 默认与可配置 auto，不新增远程发布承诺。

### L4 · P1：预算可经 resume 绕过，运行中预算尚未接线

位置：`budget.py` 的 transition_with_budget、evaluate_budget、record_tokens、set_budget；`resume.py` 的 resume_task。

本次纯 Lite 探针确认：tokens_used=11、max_tokens=10，任务受阻且恢复点为执行中时，resume_task 仍返回执行中；evaluate_budget 同时返回不通过。原因是恢复直接走普通状态迁移，没有同样预算检查。

此外，预算主要在进入执行中时检查，token 由调用者记账，缺实时执行用量与中止；allow_raise 只是参数，不等于用户授权。暂停期间是否计入墙钟时间也未形成清晰产品规则。

改进：启动、恢复、重试、新模型调用都走统一预算检查；区分恢复同一执行与开启新尝试，避免漏计或双计。接入实际 usage 或明确估算；设置单次输出上限、最大修复轮次、运行时长与停止后续派发。到达额度即停止新调用；无法精确中止时明确控制边界。提高预算经可信用户策略授权，留变更记录。明确总墙钟与活跃执行时间的口径。

### L5 · P2：工作区隔离和恢复主要仍是协议约定

create_task 写 worktree 路径，不会实际创建 Git worktree；save_task 直接写 JSON。resume 主要比较协议里的产物字符串，不是查真实进程、工作区和仓库状态。

改进：开工前创建/验证真实独立工作区与分支，校验受控路径；进程持有执行租约。保存采用原子写与适当锁，防止三角色同时读写覆盖。重启检查执行器、进程、Git HEAD、脏文件、产物及合并报告后再恢复；结果未知则受阻，不盲目重复执行。取消要停止实际运行，并保留证据，不只改状态。

### L6 · P2：角色指令和状态机不完全一致，导入验收未闭合

Developer 指令列出“需修改→待验证”，实际状态机要求先回执行中；指令应与实际修复路径统一。共享 Chief 指令中有未限定 Team 的复杂任务硬禁直派措辞，可能与 Lite 三角直派冲突。

Lite BotMRR 允许平台无法创建助手时依次扮演角色；这可用于流程演示，不能当作独立验收与正式支持。兼容 JSON、SOUL、扁平指令、BotMRR 信息量不同，不应假定导入后自动具备同样完整约束。

改进：公共职责与 profile 差异明确分离；Lite 全部开发任务保持三角路径。每种支持的导入格式验收角色身份、指令、工具权限与闭环行为；不能仅检查三个名字存在。修复 Schema 与运行字段漂移，权威定义单一来源，缺校验依赖时显式报配置问题而非静默跳过严格校验。

### L7 · P2：经验库已存在，但有效性与加载未形成闭环

现有候选、审核、发布和规则探针可以复用；review 接受调用者提供的批准，未强制关联有效性回执。发布时规则文件已存在可能不更新，store 与文件内容可能不一致；后续任务没有可信加载记录。

改进：修复任务不必等待全局规则发布；候选单独审核，绑定来源失败、适用范围、错误/正确样例与规则版本。验证后发布；按适用范围生成 Developer 开工规则清单，记录实际版本。支持停用/回滚，环境故障不自动升级成全局规则。Lite 不为此新增审查 bot。

### L8 · P2：演示脚本、测试和三平台承诺需收尾

旧 C2/C3 kit 脚本仍使用 c2fixed01、c3lesson01 等占位 commit，与真实 Git 预检不匹配；部分脚本依赖已有运行目录。合并测试中存在 assert ... or True，使相关值比较无效；其他有效断言仍存在，不能因此说全部测试无效。

兼容表仍将 GUI 导入、委派、重启以及 Windows/Linux 标为未验收。导入元数据 platforms:any 不是三平台实测证据，用户反馈某次运行成功也不能覆盖所有验收项。

改进：历史样例保留并标注，新增干净环境真实 commit 演示；去掉无效断言并正确检查集成版本的文件内容。提供跨平台 Python 入口或 Windows 原生命令，不以 Bash 脚本替代 Windows 支持。归档用户已有 demo-c4 等实测时记录具体环境、步骤和缺失项，不补写未发生结果。

## 四、实施顺序与退出条件

| 阶段 | 工作 | 必须通过的验收 |
|---|---|---|
| Lite-A：权限与可信验收 | L1/L2；操作入口、独立回执、逐轮绑定、完成门禁 | Developer 自验/假日志/旧检查/无合并标完成均被拒；合法开发与验证可执行 |
| Lite-B：合并与恢复预算 | L3/L4；统一合并门、幂等复核、恢复预算与实际用量 | failed already_merged 被拒；后置失败重试不能报完成；超预算 resume/重试不启动 |
| Lite-C：执行隔离与契约 | L5/L6；真实工作区、原子存储、重启对账、指令与 Schema | 同时更新不丢失；取消停止运行；重启不重复提交；Lite 不要求 Team 角色 |
| Lite-D：经验与演示 | L7/L8；规则回执、真实 commit、修复脚本与断言 | 首轮失败→修复→重新验证→真实合并；规则正反样例和后续加载可追溯 |
| Lite-E：独立发布 | 三平台、OMB、脱敏样例、安装与恢复说明 | 新人从干净环境单独导入 Lite 跑通；逐平台有证据；未完成则明确预览限制 |

不得通过改提示词就把程序约束标为完成；也不得为保持旧测试绿而保留已实证的绕过。新增测试应覆盖失败条件和真实交付结果，不只是字段存在。

## 五、共享修复如何与 Team 协调

权限、验收执行、SHA/attempt 绑定、合并、预算恢复、原子存储、Schema 和 lessons 属于共享底座，只开发一次，再分别跑 Lite 与 Team 验收。本报告的 Lite-A/B 与 Team 计划 T1 应合并为同一组底座修复，不能两边各造一套。

Lite 特有工作是三角直派、独立导入、自包含说明、低成本默认与单任务 Demo。Team 的 Matcha/Eng 交接、路由和 Nancy 持久待办不带入 Lite。共享字段演进保留旧任务读取或提供显式迁移，不静默改写历史验收。

## 六、发布前端到端清单

1. 干净安装、仅导入 Lite、配置一次模型/执行器与必要本机权限；得到三个独立角色及明确身份。
2. 正常任务：冻结验收→实际实现→独立验证→默认确认→本地集成→集成检查→完成回执。
3. 失败任务：第一次失败留证→Developer 修复→新 attempt 重新验证→成功交付，不覆盖失败记录。
4. 反例：伪造执行、错 SHA、缺日志、旧报告、验收变更、越权写入、无合并标完成全部拒绝。
5. 合并异常：冲突、目标基线前进、后置失败、重复请求、不确认；不意外推远程，不破坏用户工作分支。
6. 预算异常：调用耗尽、次数到限、超时、恢复与重试；没有新的授权不能抬限或继续执行。
7. 实际杀进程/断网/应用重启/取消；对账后恢复或明确受阻，不拿协议层模拟当真实恢复证据。
8. 经验正反样例与后续任务加载；中文/空格路径、编码、跨平台命令；macOS/Windows/Linux 分别记录。

默认只运行需要的角色，不全员循环聊天；阶段汇总、Git 检查与计数尽量由程序完成。Lite 无须新增国内消息平台，但模型端点/执行器配置保留公共接口；只宣布实际验证的组合。

## 七、交付与本次验证边界

交付：共享底座修复、Lite 指令与独立导入包、权威契约、真实执行/合并/预算恢复证据、修订演示、三平台支持矩阵、新手安装和故障恢复文档。公开样例不得含用户私人路径、账号、密钥或未授权业务内容。

本次依据源代码审阅及临时 Lite 探针提出计划；本次确认了“无真实测试/合并也能经普通接口标完成”和“预算超限仍可 resume 至执行中”。共享合并漏洞沿用同基线 Team 审查的临时 Git 实证。现有 kit 72 项测试在 Team 审查时通过；本次没有代码变动，不重复以测试数量证明新增验收覆盖。

没有执行真实 OMB GUI、多平台或模型提供方验收。业务代码未修改，用户运行目录未改，计划未实施。后续进度以实际行为、证据和逐平台结果汇报，不报缺乏依据的完成百分比。
